# 图片读取延迟初测（2026-11-24）

本机 WLAN 访问线上版本 `6dd30d3`：桌面首屏第一张封面在 2.21 秒就绪，三张可见封面在 2.74 秒就绪；单张公开 JPEG 串行下载为 0.44–0.48 秒。首屏等待既包含发图请求前的页面与列表加载，也包含多图请求开始后的等待。现有客户端样本**不能单独量出 COS 耗时**，不据此判定 COS 是瓶颈。

## 环境与方法

- 2026-11-24 北京时间 18:14–18:16；Windows 本机同一 WLAN，通过本机 `hosts` 解析站点域名，直连线上 HTTPS 并正常校验证书，无代理或模拟限速。包含实际公网传输，不含公共 DNS 查询。
- Edge `158.0.4370.33`（HTTP/2），每个视口用独立未登录会话：桌面 `1440×900` 一轮首页、滚动、进店、放大、返回；`390×844` 触屏模拟一轮首页，仍在同一电脑和网络，不是真机或蜂窝样本。
- 首页时间从导航开始；交互时间从自动化动作发出前开始。浏览器逐动画帧检查进入视口（横纵各至少 8 像素）、样式可见、`img.complete` 且有有效宽度的照片。计为「就绪」，不等同于逐像素绘制时间；占位图不计入。请求阶段来自浏览器资源计时。
- `curl.exe` 8.13.0（HTTP/1.1）对三张当天在页面中出现的公开图片各做两次串行 `GET`。每次单独启动进程，不复用 TCP/TLS；响应体写入 `NUL`，计入完整下载时间。没有直接访问 COS 接口、写入业务数据、修改服务器或做批量压测。

- **静态资源已可长时间缓存，但本次冷传输未压缩。** 浏览器收到的启动 JS/CSS 没有 `Content-Encoding`，记录的传输体与解码体同大小。另对入口 JS 和全局 CSS 各做一次只读 `HEAD`，明确声明接受 `gzip, br`，仍无 `Content-Encoding`。同会话新标签页的 7 个启动资源均命中磁盘缓存；HTML 收完到列表发出由约 1,165 毫秒变为约 103 毫秒。但这轮 HTML 自身首包比冷启动慢得多，不能拿两次总耗时当优化前后对照，也不能据此归因 HTML 波动。
- **封面地址到账后仍发得很快。** 两轮列表收完到第一批封面请求约 35、43 毫秒，和初测约 25 毫秒一致处于几十毫秒量级。下面对照静态 JS/CSS 压缩前后的传输字节数和启动时间；这不等同于优化图片 API 的首包。

## 修改建议与验收

1. **静态压缩已上线并通过首轮验收。** 继续限定在 `/assets/` 的静态 JS/CSS，保留仓库模板和线上 HTTPS 配置一致；如需评估实际用户收益，补真机和多轮全新会话对照。
2. **先小范围验证只在读取时缩小首页商户封面。** 以 480 档为首个候选；保留私有 COS、原图 URL 和现有可见性检查。详情与放大仍用原图。按需缩放会增加上游等待，先在本站完整链路验证弱网收益和失败回退，不先持久化派生图；若额外首包成为瓶颈再比较预生成。验收覆盖旧图、撤下封面、图片失败、真机清晰度、首屏和滚动。暂不统一改所有点评图、头像和小程序，也不先改懒加载策略。
3. **磁盘缓存等应用实测。** 单图已从真实服务器直读 COS；还需用请求 ID 对齐 Nginx 上游响应头、应用可见性与元数据查询、COS SDK 完整读取，核对正常流量下的连接复用和重复图片比例，再判断是否值得缓存。若落地，先做容量上限和淘汰，校验通过才可查缓存，避免并发重复回源、半文件和磁盘故障拖垮请求；浏览器 `no-store` 和 ETag 暂不调整。
