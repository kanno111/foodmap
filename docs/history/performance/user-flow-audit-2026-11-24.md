# 访客流程测速与首页启动优化（2026-11-24）

这轮不改图片、搜索规则或部署配置。最明确的前端等待是首页入口模块就绪后，还要再请求小型首页 JS/CSS，取回后才发店铺列表请求。将首页路由并入启动模块后，隔离对照里 6 轮列表请求均提前，中位配对差约 81 毫秒。详情的非必要请求和地图初始化仍是后续候选，不把单机小样本当全站性能结论。

## 线上只读观察

Windows 本机 Edge `158.0.4370.33`，用本机 `hosts` 直连线上 HTTPS，无代理、模拟限速或登录。桌面 `1440×900` 走首页、搜索、详情及返回、地图；窄屏 `390×844` 从新会话开首页并滚动。另一次直接开榜单，以及一次地图拖动采样。浏览器定位条件用于检测 DOM 或接口，不以脚本轮询到达时间冒充精确像素绘制、真机 INP 或 P95。

| 场景 | 本机观察 |
| --- | --- |

## 首页模块提前加载

`frontend/src/app/router/index.ts` 直接导入首页组件，其他路由保持动态加载。原构建的首页包装模块仅约 0.45 kB JS 和 0.68 kB CSS，但需要在入口模块已经加载后才能发现。这样调整减少的是阻塞列表请求的网络往返，不是改变列表接口耗时。

使用同一环境分别构建两个版本，在回环 HTTP/1.1 上使用相同的 gzip 配置和模拟 API。Edge 每轮全新会话且关闭缓存，模拟 8 Mbps 下行与 60 毫秒延迟；交替先后顺序。首页 6 对、直接打开榜单 3 对。记录从导航开始到业务 API 请求启动，不将差值叠加到此前 gzip 或缩略图实验。

| 场景 | 静态 JS/CSS | 对应 API 发出，中位数 |
| --- | --- | --- |
| 首页 | 7 → 5 个请求，257,011 → 256,049 字节 | 596.7 → 515.8 毫秒；逐对提前 62.4–111.3 毫秒 |
| 榜单直开 | 仍是 6 个请求，增加 178 字节 | 610.1 → 575.0 毫秒；有快有慢，不宣称另有提速 |

6 个前端定向测试文件共 59 项通过，生产模式类型检查和构建通过。两组浏览器夹具均从预期接口取得 `200` 并进入可用页面，榜单模块仍单独按需请求。没有修改线上部署或等待 CI/CD，这一改动尚未发布。

## 后续优先级

1. **详情页回复预览**：先测有回复、无回复和更多点评的店铺。如果逐条预取扩大首屏流量，优先不读屏外预览或合并预览读取，但保留原有回复展示和进入详情行为；不根据这一个样本重写整个回复流程。
2. **地图初始化**：先在低端手机或固定 CPU 限速下复测。区分高德 SDK 的长任务、首次点位读取与拖动后的延迟，不先缩短防抖或换地图方案。
3. **启动包**：Vite 仍提示店铺投稿组件同时被静态、动态导入，实际没有拆出独立块。后续检查公共入口为何引入它；本轮只处理首页包装模块，避免把拆包回归混入。
